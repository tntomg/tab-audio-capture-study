# Отчет по архитектуре хранения, воспроизведения и кибербезопасности аудио (на примере Udio)

## 1. Введение и цели исследования

Настоящий отчет подготовлен на основе комплексного анализа сетевого взаимодействия, структуры бэкенд-ответов, клиентских JavaScript-бандлов Next.js и подсистемы защиты контента платформы генеративной музыки **Udio**.

**Ключевой исследовательский вопрос:**
Каким образом современные медиаплатформы организуют хранение и воспроизведение звуковых файлов, почему в сетевом трафике браузера отсутствует статичный `.mp3`-файл даже при полном воспроизведении песни, и как устроена модель угроз перехвата аудиосигнала.

---

## 2. Архитектура хранения исходников (Storage Layer)

В сервисах уровня Udio хранилище мастер-файлов полностью изолировано от публичной сети.

1. **Объектное хранилище (Google Cloud Storage):**
   * Сгенерированные треки помещаются в специализированный бакет: `udio-artifacts-...`.
   * Прямой путь к объекту:
     ```text
     https://storage.googleapis.com/udio-artifacts-c33fe3ba-3ffe-471f-92c8-5dfef90b3ea3/samples/{generation_id}/{variant}/{song_name}.mp3
     ```
2. **Политика управления доступом (IAM & Private ACL):**
   * Анонимный доступ (`allUsers`) к объектам хранилища отключен.
   * Любой прямой HTTP-запрос (GET / HEAD) к файлу возвращает:
     ```xml
     <Error>
       <Code>AccessDenied</Code>
       <Message>Access denied.</Message>
       <Details>Anonymous caller does not have storage.objects.get access...</Details>
     </Error>
     ```
3. **Метаданные трека в Next.js (SSR / REST API):**
   * При серверном рендеринге страницы (`/songs/{song_id}`) и при обращении к API (`/api/songs?songIds=...`) возвращается JSON-объект трека, содержащий ключ `song_path`.
   * Поле `song_path` служит внутренним идентификатором мастер-артефакта в инфраструктуре бэкенда, а не публичной ссылкой для скачивания клиентом.

## 3. Архитектура доставки и фрагментации (Delivery & Packaging Layer)

Udio **не транслирует цельный MP3-файл** через браузер. Вместо этого применяется адаптивный потоковый протокол **HLS (HTTP Live Streaming)** на базе фрагментированного MP4 (CMAF, контейнеры `.m4s`).

1. **Стриминговый шлюз:**
   * Все медиапотоки обслуживаются через изолированный домен: `https://stream.udio.com` под защитой Cloudflare CDN.
2. **Пакетирование (Packaging):**
   * Контент упаковывается с помощью **Shaka Packager** (`shaka-packager v3.4.2`).
3. **Манифесты воспроизведения:**
   * Клиентский плеер формирует запрос к мастер-манифесту:
     ```text
     GET https://stream.udio.com/stream/{song_id}
     ```
   * В ответ возвращается HLS-плейлист (`application/vnd.apple.mpegurl`):
     ```text
     #EXTM3U
     ## Generated with https://github.com/shaka-project/shaka-packager version v3.4.2
     #EXT-X-INDEPENDENT-SEGMENTS
     #EXT-X-MEDIA:TYPE=AUDIO,URI="/api/v2/audio-stream/content/{song_id}/manifest.m3u8",GROUP-ID="audio",NAME="stream_0"
     ```
   * Субплейлист (`manifest.m3u8`) делит трек на:
     * **Инициализационный сегмент** (`init.mp4`) — содержит заголовки кодека (AAC-LC, `mp4a.40.2`), частоту дискретизации (44.1 кГц) и раскладку каналов.
     * **Медиасегменты** (`segment_1.m4s`, `segment_2.m4s`...) — блоки сжатого аудио длительностью по 6–8 секунд.

## 4. Подсистема защиты контента (DRM & Encryption Layer)

Фрагменты аудиопотока не передаются в открытом виде. В субплейлисте явно указано шифрование сэмплов:

```text
#EXT-X-KEY:METHOD=SAMPLE-AES,URI="data:text/plain;base64,...",KEYID=0x...,IV=0x...,KEYFORMAT="urn:uuid:edef8ba9-79d6-4ace-a3c8-27dcd51d21ed"
#EXT-X-KEY:METHOD=SAMPLE-AES,URI="skd://...",KEYFORMAT="com.apple.streamingkeydelivery"
```

1. **Метод шифрования:** `SAMPLE-AES` (шифруются элементарные аудиосэмплы внутри медиаконтейнера алгоритмом AES-128).
2. **Платформа Multi-DRM:** Udio интегрирован с сервисом **BuyDRM KeyOS** (домен `*.keyos.com` в директиве `connect-src` CSP).
3. **Две схемы лицензирования:**
   * **Google Widevine Modular** (для Chrome, Edge, Firefox, Android) — схема `urn:uuid:edef8ba9-79d6-4ace-a3c8-27dcd51d21ed` с PSSH-заголовком.
   * **Apple FairPlay Streaming** (для Safari, iOS, macOS) — схема `skd://` (`com.apple.streamingkeydelivery`).
4. **Обмен лицензиями:**
   * Сертификаты: `/drm/cert/widevine?version=3` и `/drm/cert/fairplay`.
   * Запрос ключей дешифрования: эндпоинты `/drm/license?type=widevine` и `/drm/license?type=fairplay`.

## 5. Клиентский движок и развенчание мифа о «файле в памяти»

Существует распространенное заблуждение: *«раз песня звучит в динамиках целиком, значит где-то в оперативной памяти браузер собрал цельный MP3-файл»*. В современных веб-архитектурах это устроено принципиально иначе.

### Конвейер воспроизведения (Media Pipeline)

```
[Чанки .m4s из сети] 
        │
        ▼
[MediaSource API (SourceBuffer)]   ← Скользящее буферное окно в RAM (15-30 сек)
        │
        ▼
[Demuxer & CDM / Декодер]          ← Расшифровка в изолированном CDM и декодирование в PCM
        │
        ▼
[Аудиодрайвер ОС (WASAPI / ALSA)]  ← Кольцевой буфер сырого звука (размер: десятки мс)
        │
        ▼
[ЦАП звуковой карты]               ← Преобразование в аналоговый сигнал (динамики)
        │
        ▼
[Garbage Collection]               ← Проигранные сэмплы мгновенно затираются в RAM
```

1. **Media Source Extensions (MSE):**
   * Браузер не пишет чанки на диск. JavaScript-библиотека **Google Shaka Player** (`shaka-player`) скачивает очередной чанк и методом `SourceBuffer.appendBuffer()` передает сырые байты в нативный движок браузера.
2. **Декодирование «на лету» в PCM:**
   * Формат MP3/AAC перестает существовать в момент демультиплексирования. Защищенный модуль **CDM** (*Content Decryption Module*) расшифровывает сэмплы и сразу направляет их в декодер.
   * На выходе декодера формируется **PCM** (*Pulse Code Modulation*) — непрерывный поток несжатых числовых значений амплитуды звуковой волны.
3. **Бесшовное воспроизведение (Timestamps):**
   * Внутри сегментов `.m4s` содержатся временные метки **PTS** (*Presentation Timestamp*). Движок плеера стыкует границы блоков с точностью до единичного сэмпла, исключая щелчки и паузы.
4. **Утилизация памяти:**
   * Аудиодрайвер держит в буфере лишь крошечный фрагмент (20–100 мс). Как только звук воспроизведен звуковой картой, память освобождается. Полный файл ни в какой момент времени в RAM не существует.

## 6. Модель угроз и кибербезопасность звуковых данных

### 6.1. Анализ предположения о «перехвате и объединении чанков из RAM»

Попытка извлечь данные из оперативной памяти для сборки файла наталкивается на технические барьеры:
* **Чанки до декодирования:** остаются зашифрованными AES-ключами. Их бинарное объединение дает лишь поврежденный нечитаемый файл.
* **Поток после декодирования:** представляет собой чистый PCM без метаданных и контейнера. Объединить его «как готовый файл» невозможно — требуется непрерывная запись потока в реальном времени с последующим прогоном через программный аудиоэнкодер (WAV/MP3).

### 6.2. Уязвимые места архитектуры (Threat Vectors)

| Уровень | Угроза | Реализуемость | Защитный механизм |
| :--- | :--- | :--- | :--- |
| **1. Сеть** | Перехват трафика (Sniffing) | Высокая | TLS/HTTPS + шифрование чанков (SAMPLE-AES). Перехваченный трафик бесполезен без ключа. |
| **2. Браузер** | Извлечение через JS-инъекции / DevTools | Средняя | Интерфейс EME изолирует ключи и дешифрованные данные внутри закрытого модуля CDM. JS-контекст не имеет доступа к сырому звуку. |
| **3. Аудиосистема ОС** | Программный перехват звукового тракта (WASAPI Loopback, Virtual Audio Cable) | **Высокая** (Основной вектор) | На ПК с Widevine L3 расшифрованный PCM попадает в системный микшер ОС. Специализированные драйверы записи могут захватить этот поток со скоростью 1x. |
| **4. Выход ЦАП** | Аппаратная «Аналоговая дыра» (Analog Hole) | **Критическая** | Захват аналогового сигнала с выхода наушников/динамиков внешним рекордером. Технически неизбежен. |

### 6.3. Инженерные методы противодействия и защиты

Поскольку предотвратить программный или аналоговый перехват на клиентском устройстве на 100% математически невозможно (пользователь обязан слышать звук), в индустрии применяются превентивные и форензик-технологии:

1. **Аудио-стеганография и цифровые водяные знаки (Audio Watermarking):**
   * В частотный спектр трека подмешивается неслышимый человеческому уху криптографический маркер (ID пользователя, хэш сессии, временная метка).
   * **Результат:** Даже если звук перехвачен через виртуальный кабель или аналоговую запись, специальный алгоритм анализа извлекает водяной знак и однозначно идентифицирует скомпрометированный аккаунт.
2. **Аппаратная защита пути воспроизведения (Hardware DRM / PUMA):**
   * Применение Widevine L1 / Apple FairPlay с изоляцией в защищенной среде процессора (TEE / Secure Enclave).
   * Декодирование и передача на ЦАП происходят по защищенной шине, блокирующей перехват штатными средствами ОС.
3. **Поведенческий анализ и Rate Limiting (Anti-Scraping / WAF):**
   * Мониторинг паттернов потребления: серийное воспроизведение без пауз, аномальная активность сессий, одновременные стримы с одного IP.
   * Динамическая аннуляция токенов лицензирования DRM при фиксации автоматизированных запросов.
